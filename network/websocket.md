# 웹소켓
서버와 클라이언트 간 양방향 소통 가능.
한번 연결하면 끊지 않고 계속해서 빠르고 자유롭게 데이터를 주고받을 수 있다.

Q. 연결한다는 게 뭔가? 
서로 전달할 데이터의 크기, 암호화의 방식, 사용할 프로토콜 등을 똑같이 세팅해서 오류없이 전달 및 해독할 수 있게 하는 과정.

Q. 다른 통신 방식은 무엇이 있는가?
ㅍ웹소켓과 HTTP를 넘어선 다양한 통신 선택지

상황과 목적에 따라 개발자들은 HTTP와 웹소켓 외에도 다음과 같은 강력한 무기들을 골라 사용.

1. 서버가 일방적으로 밀어줄 때: SSE (Server-Sent Events)

앞서 잠깐 등장했던 '라디오 방송' 같은 기술입니다.
특징: 일반 HTTP 연결을 열어두고, 서버가 클라이언트에게 텍스트 데이터를 지속적으로 스트리밍(Push)합니다. 단방향입니다.
언제 쓰나요?: 주식 실시간 호가창, 뉴스 피드 알림, ChatGPT가 글자를 한 글자씩 타다닥 찍어주는 기능.
장점: 웹소켓보다 훨씬 가볍고, 브라우저가 알아서 재연결을 해줍니다.

2. 브라우저끼리 직접 통신할 때: WebRTC (Web Real-Time Communication)

서버를 거치지 않고 '사용자(클라이언트)와 사용자'를 직접 연결하는 P2P(Peer-to-Peer) 기술입니다.
특징: 서버는 처음에 서로의 IP 주소를 교환하게 해주는 '중매쟁이(Signaling)' 역할만 하고 빠집니다. 그 이후엔 둘이서 직접 데이터를 주고받습니다.
언제 쓰나요?: Zoom, Google Meet 같은 화상 회의, 디스코드 보이스 채팅.
장점: 중간 서버를 안 거치니 압도적으로 빠르고 서버 비용이 획기적으로 줄어듭니다. 영상/음성 같은 무거운 데이터를 보낼 때 필수입니다.

3. 백엔드 서버끼리 대화할 때: gRPC (Google Remote Procedure Call)

구글이 만든 '서버 간 통신의 표준'입니다. 마이크로서비스(MSA) 아키텍처에서 백엔드 서버끼리 통신할 때 일반 HTTP 대신 씁니다.
특징: 데이터를 보낼 때 우리가 읽을 수 있는 JSON(텍스트) 대신, 컴퓨터가 가장 좋아하는 0과 1의 바이너리(Protobuf)로 압축해서 보냅니다. 통신 규칙은 HTTP/2를 사용합니다.
언제 쓰나요?: 넷플릭스나 배달의민족처럼 수백 개의 백엔드 서버가 서로 데이터를 미친 듯이 주고받아야 할 때.
장점: 일반 HTTP/JSON API보다 속도가 체감상 7~10배 이상 빠릅니다.

4. 사물인터넷(IoT) 환경일 때: MQTT

아주 가볍고 전력 소모가 적은 '사물인터넷용 카카오톡'입니다.
특징: 대역폭(인터넷 속도)이 매우 낮고 불안정한 환경에서 동작하도록 설계된 가벼운 발행/구독(Pub/Sub) 프로토콜입니다.
언제 쓰나요?: 스마트 홈(전등 끄기/켜기), 커넥티드 카(테슬라 차량 원격 제어), 공장 온도 센서.
장점: 헤더(편지 봉투) 크기가 2바이트밖에 안 될 정도로 가벼워서 배터리와 데이터를 거의 안 씁니다.

5. 인정사정없는 극강의 속도가 필요할 때: UDP 소켓

핸드셰이크고 나발이고 다 생략하고 '일단 던지고 보는' 통신입니다.
특징: TCP(HTTP, 웹소켓의 기반)는 데이터가 가다가 유실되면 다시 보내달라고 요청하지만, UDP는 그런 거 없이 냅다 쏘기만 합니다. 유실되어도 책임지지 않습니다.
언제 쓰나요?: 리그 오브 레전드(LoL), 발로란트, 오버워치 같은 0.01초가 중요한 실시간 FPS/액션 게임.
장점/단점: 엄청나게 빠르지만, 중간에 패킷(데이터)이 사라지면 캐릭터가 순간이동(버벅임)하는 현상이 생깁니다.

- 아키텍트의 선택 요약
버튼 눌러서 데이터 가져오기: 일반 HTTP (REST API)
실시간 채팅, 양방향 게임: WebSocket
서버가 알림만 보내주기: SSE
얼굴 보고 대화하기(화상): WebRTC
백엔드 서버들끼리 대화하기: gRPC
냉장고, 자동차 원격 제어: MQTT

Q. 어떻게 그것이 가능한가? 
지속적으로 공간을 확인하는 스케줄링 방식이 아니다. 그건 http 환경에서 실시간 흉내를 내려던 폴링 방식이다. 이벤트 기반 동작.
웹소켓은 데이터가 TCP 소켓에 들어오면(아마 tcp 소켓이 랜카드 하드웨어 안에 들어가있는 연결통로 저장공간인듯), os가 이를 전기적 신호로 감지해서, 해당 프로그램에 알려준다. 이를 인터럽트라고 함.
즉, 하드웨어 계층에서 "랜카드의 수신" 단계. 데이터가 인터넷 선을 타고 컴퓨터의 랜카드에 들어온다. 랜카드가 전기적 신호로 cpu에게 데이터 왔다고 찌른다. 이를 하드웨어 인터럽트라고 한다. 운영체제 계층에서 랜카드에서 데이터를 가져와서 TCP/IP 포장을 뜯고 이 데이터가 어느 프로그램의 데이터인지 확인하고 os 메모리 공간 안의 소켓 버퍼에 데이터를 밀어넣는다. 그리고 애플리케이션에 소켓리스트를 전달하는 것은 os가 알람을 모아 인터럽트 코얼레싱 같은 최적화 기술로 적절하게 데이터를 리스트로 넘겨준다.  cpu가 그 리스트를 전달하고, 돌아와서 잠드는 사이에 데이터가 랜카드에 들어오고 cpu를 찌를 수 있지만, 그 데이터는 os의 소켓버퍼에 채워지고 준비완료 큐에 다음 처리할 데어터를 넣어 놓는다.

Q. 그렇다면 쓰지 않는 이유는 무엇인가?
실시간 메신저, 채팅, 실시간 주식 시세창, 여러명 동시 접속 멀티 플레이어 게임, 구글 문서 같은 실시간 공동 편집 도구, 실시간 스코어 및 댓글 등.
