# 로드밸런서
"서버 여러 대에 요청을 나눠주는 장치"
"서버 장애 시 다른 서버로 트래픽을 보내 가용성을 높이는 장치"

질문. 트래픽을 어느 서버로 보내는가? (알고리즘)
서버의 상태는 항상 동일한가? 내 요청이 다른 서버로 들어가도 문제가 없는가?
로드밸런서가 죽으면?

장애원인을 로드밸런서에서 찾을 수 있나? (gpt)

로드밸런서는 무중단배포와 연관되어있다. 
새 서버 띄우고 -> health check 통과 -> 로드밸런서가 새 서버에 트래픽을 보내고 -> 기존 서버 drain (중지) -> 기존 요청 처리 완료 후 종료
배포 순간 사용자 요청 끊기지 않게
아직 준비 안된 서버에게 트래픽이 가지 않게
서버 종료했는데 새 요청이 들어오지 않게

ecs, eks, ec2 auto scaling, blue-green, canary 배포를 말하려면 로드밸런서 이해가 필수.

세션과 인증설계. 만약 a 서버에 인증을 해서 세션을 저장한 경우, b 서버에는 세션이 없어서 로그아웃처럼 보인다. b서버에 요청이 가면 안됨.
선택지들이 있다. sticky session, redis, jwt 기반 stateless 인증

요청 경로를 보면
사용자 요청 -> DNS -> CDN -> 로드벨런서 -> nginx / api gateway -> application server -> db/redis/Queue

아래 정도만 공부하기.
1. L4 로드밸런서와 L7 로드밸런서 차이
2. Round Robin, Least Connection, IP Hash 같은 분산 방식
3. Health Check가 무엇을 기준으로 서버를 살았다고 판단하는지
4. Sticky Session이 왜 필요하고 왜 위험한지
5. Timeout, idle timeout, connection timeout의 의미
6. TLS termination 구조
7. X-Forwarded-For / X-Forwarded-Proto 헤더
8. Blue-Green / Rolling 배포에서 로드밸런서가 하는 역할
9. WebSocket, SSE, 파일 업로드 같은 긴 연결에서 생기는 문제
10. 로드밸런서 자체의 SPOF와 클라우드 managed LB의 의미

그래서 실무에서 이런 걸 알면 됨
서버가 죽었을 때 어떻게 감지할 것인가?
배포 중 요청을 어떻게 끊기지 않게 할 것인가?
같은 사용자의 상태는 어디에 둘 것인가?
긴 요청과 WebSocket은 어떻게 처리할 것인가?
로드밸런서 뒤에서 원래 사용자 IP와 HTTPS 정보를 어떻게 보존할 것인가?
어떤 timeout 때문에 장애가 나는가?
